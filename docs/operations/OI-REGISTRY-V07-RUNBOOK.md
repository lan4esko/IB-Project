# Тестовое обновление OI Registry до v0.7.0-rc1 на Debian

**Исходный проект:** `/home/admsec/ZGT-v06-test/CMDB/oi-registry-v0.1`.
**Единственный целевой Compose project:** `oi-registry-v06-test`.
**Рабочий `oi-registry` и `ib-platform` не затрагивать.**

## Особенности

`backend/Dockerfile` запускает `alembic upgrade head` **автоматически при старте `oi-api`**. Поэтому `docker compose up` на обновлённом коде изменяет схему PostgreSQL до `0011_svt_media_protection`. Миграции `0010` и `0011` не удаляют существующие записи. Работа на реальном PostgreSQL ещё не подтверждена. Перед запуском желательно иметь проверенную копию БД; владелец стенда вправе сознательно пропустить этот этап, принимая риск отсутствия гарантированного отката.

## Команды (после размещения архива в `/media/sf_/`)

```bash
cd /home/admsec/ZGT-v06-test
sha256sum /media/sf_/OI-Registry-v0.7.0-rc1.tar.gz
# Сверить SHA с опубликованным манифестом из архива загрузки
# Проверить незакоммиченные изменения:
git status --short
# Распаковать только в ТЕСТОВОЕ дерево:
tar -xzf /media/sf_/OI-Registry-v0.7.0-rc1.tar.gz -C /home/admsec/ZGT-v06-test
cd CMDB/oi-registry-v0.1
docker compose -p oi-registry-v06-test config -q
docker compose -p oi-registry-v06-test up -d --build --no-deps --force-recreate oi-api oi-web
docker compose -p oi-registry-v06-test ps
docker compose -p oi-registry-v06-test exec -T oi-api alembic current
curl -i http://127.0.0.1:18085/api/health/ready
```

Ожидаемый Alembic: `0011_svt_media_protection (head)`. Рабочий проект отдельно: `docker compose -p oi-registry exec -T oi-api alembic current` → `0006_control_rules (head)` (если с тех пор не обновлялся).

Если API упал — **не запускать `docker compose down -v`**. Смотреть `docker compose -p oi-registry-v06-test logs --tail=100 oi-api`. Не пытаться `alembic downgrade` на живых данных; откат требует проверки схемы и отдельного плана восстановления.

## Приёмка GUI

1. `18085`: вход, проверка заголовка `v0.7.0-rc1`.
2. Администратор → «Конструктор полей»: добавить типовое текстовое поле в Заявки, другое поле в СВТ. Создать СВТ и заявку, заполнить пользовательские поля, проверить журнал истории.
3. Администратор → «Реестр СВТ» / «Конструктор полей»: выгрузить стандартный CSV, выбрать режим `merge`, получить предпросмотр и отдельное подтверждение. Повторить на тестовых записях режимы `copy` и `replace` с проверкой сохранения ремонтов. Не импортировать производственный CSV на тестовый стенд без проверки сведений.
4. «Реестр СВТ» → карточка СВТ → «МНИ / ЗМНИ»: зарегистрировать два МНИ с разными заводскими/учётными номерами, один ЗМНИ, обновить дату и имя файла-контейнера, проверить «История».
5. «Объекты ОИ» → карточка → «Проверки и нарушения»: создать проверку, указать SMB-путь, добавить два замечания, отметить устранение одного. Убедиться, что второе осталось открытым.
6. «Построитель запросов»: выбрать колонки `code`, `network_segment`, глобальное поле администратора, задать фильтр и экспортировать CSV.
7. `curl -i` на `/api/health/ready`, проверить журнал API, защиту CSRF и невозможность редактору создавать админские поля/импортировать CSV.

## HTTPS

В пакет v0.7 не включён автоматический переключатель на HTTPS: следовать [регламенту v0.6.1](OI-REGISTRY-V061-HTTPS.md), проверить TLS и проброс TCP с VirtualBox. Подменять HTTPS пробросом обычного HTTP нельзя. Статус HTTPS отмечать в протоколе приёмки отдельно.
