# Безопасность, разграничение доступа и эксплуатация без Интернета

## Принципы

- Сетевые потоки разрешать по утверждённой топологии. `127.0.0.1:8085` в OI Registry не означает автоматического доступа извне VM.
- Хранить `.env` и SSH/SMB/API secrets **вне Git**, с правами `0600`, архивы и их каталоги ограничить `0600/0700`. Все резервные копии с `config.env` шифровать для внешнего носителя.
- Администраторы используют личные УЗ; локальные OS root полномочия обладают полным доступом к Docker и БД, их нельзя ограничить только ролями веб-приложения.
- Роли OI (`admin`, `editor`, `requester`) предотвращают ошибочные действия через API, **не заменяют системный hardening БД, хоста и сети**.
- Хранить журнал действий без разрешения операторам его править. Учитывать, что прикладной `audit_events` без внешнего append-only/WORM **не является криптографически неизменяемым** против root/DBA.
- Нормативные документы и информация об ОИ могут различаться по режиму доступа; пилот IB AI не использовать для гостайны.

## Изолированный контур / цепочка поставки

1. До переноса в контур зафиксировать версии Debian пакетов, Docker/Compose, Python wheels, OCI images с **digest**, моделей Ollama, сертификатов и хэши релизов; не полагаться на `latest` и `stable-alpine`.
2. Сформировать офлайн-репозиторий образов (внутренний registry либо архивы `docker save` / `docker load`), apt mirror или полный approved set `.deb`, wheelhouse для Python, manifest SHA256.
3. Проверить программное обеспечение и носители по установленному регламенту ИБ до ввода, журналировать перенос и происхождение материалов.
4. Обеспечить локальные DNS/NTP и доверенные CA, особенно при HTTPS к OpenProject, Kerberos/AD и журналировании.
5. Внешняя проверка актуальности НПА выполняется вне изолированного контура по отдельной процедуре, после чего в контур импортируются проверенные редакции и их хэши.
6. Для восстановления иметь автономно не только БД, но и установщики/контейнерные образы/пакеты — без сети `docker compose build` может зависнуть при pull базового образа.

## Актуальные ограничения

- Не внедрено полноценное per-OI разграничение для всех форматов/видов доступа: OI Registry v0.4 требует дополнительной оценки перед внесением конфиденциальных данных.
- OI Gateway/Open WebUI не передаёт надёжную личность конечного человека для персонального аудита ответов без SSO.
- SMB/AD Document Hub v0.6 находится в проекте; не создавать учётку без санкции владельца AD.
- В журнале проделанных работ есть `performed_by` и `actor_id`; эти атрибуты не доказывают физического присутствия конкретного человека.
- Пароли OpenProject API, Postgres, Session secret не должны попадать в `docker compose config` stdout, команды чата, скриншоты и Git.

## Безопасный внешний обмен

Публикуйте только очищенный вывод статусов (`docker compose ps`, Alembic current, HTTP-code). Перед передачей логов применяйте локальное обезличивание IP/логинов/содержимого документов и секретов. Исходные доказательства и дампы хранить отдельно в защищённой зоне.

## Контрольный список hardening

Ревизия `docker.sock` и членства в группе docker, systemd-сервисов и unit permissions, permissions `.env`, персональных ключей, TLS, Nginx headers и cookies, времени, журналов и сроков хранения, SQL прав пользователей сервисов, firewall, закрытых backup volumes, доступа к Git. Этот список **рекомендован к проверке**, а не автоматически выполнен релизом v0.4.
