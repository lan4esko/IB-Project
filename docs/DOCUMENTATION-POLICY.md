# Регламент актуализации документации при каждом обновлении

**Цель:** сменяющий администратор без Интернета способен понять состав систем и восстановить работу. Документация — не отложенная задача, а состав релиза.

## Обязательные действия автора релиза

1. До правки: зафиксировать известную топологию, миграцию, конфигурацию без секретов, Git commit и backup.
2. После изменения кода: обновить затронутые разделы `docs/systems/`, `docs/operations/`, `docs/integrations/`, `docs/data/`, Mermaid диаграммы; указать `[ФАКТ]/[ИСХОДНИК]/[ПЛАН]`.
3. **Всегда при версии/значимом изменении** обновить `docs/CHANGELOG.md` и `docs/RELEASES.md`; создать `docs/releases/<версия>.md` с изменениями, миграциями, совместимостью и rollback.
4. Выполнить локальные тесты, `python3 docs/scripts/verify_docs.py`, smoke приложения, проверку backup, журналировать результаты.
5. Применять **одним коммитом** исходники приложения, migrations, тесты и документацию. При изменении DB schema отдельно описать способ восстановления/миграции; Git не откатывает данные.
6. Перед принятием merge в `main` проверять `docs/scripts/pre-commit-docs.sh` и чеклист релиза. Без подтверждения doc review версию не считать завершённой.

## Технический механизм

- `install_git_hook.sh` устанавливает в **локальный** Git pre-commit hook; при stage важных изменений исходников `CMDB/oi-registry-v0.1/`, `AI/ib-platform/` и `open-project/` потребует одновременно staged обновления `docs/CHANGELOG.md` и `docs/RELEASES.md`.
- `verify_docs.py` проверяет обязательные файлы, локальные относительные ссылки и отсутствие в содержимом docs типовых записей реальных секретов (эвристика, не DLP). Эта проверка не сможет гарантировать, что описание корректно: это ответственность автора и принимающего администратора.
- Hook может быть обойдён `--no-verify` или не сработать на другом компьютере, пока его там не установили. Для жёсткой дисциплины аналогичную проверку внедряют в **локальный CI**, который недоступен к обходу разработчиком.
- `new_release.py` создаёт шаблон и запись в журналах, но **не выдумывает** реализованное поведение. Заполнить поля вручную.

## Владение и правила приёмки

Автор кода отвечает за актуальность изменений функций; эксплуатирующий администратор проверяет реальные команды и пути, ответственный ИБ — модель доступа/секреты/аудит, владелец проекта — RTO/RPO и цели. Протокол изменений с датой, версией и исполнителем хранить в локальном реестре, не дублировать персональные данные в публичном Git.

## Состояние актуальности

При расхождении информации в документации и на живом сервере сперва регистрировать несоответствие, затем собирать локальный снимок `collect_inventory.sh`, проверять что произошло, и исправлять doc в Git. **Не переписывать факт под желаемую модель**.
