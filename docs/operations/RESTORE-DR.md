# План аварийного восстановления (DR) в изолированном контуре

**Не выполняйте первые восстановительные операции на боевой VM.** Первое тестирование — на отдельном чистом стенде в отключённом от production контуре; цель: доказать возможность прочитать документы, войти в UI, проверить журналы и задачи. Сохраняйте оригинал инцидентного диска/volume для расследования.

## RTO/RPO

Точные допустимые простои и потери данных **не утверждены**. Их должен определить владелец каждой ИС. Пока RPO равен времени от последней **проверенной** резервной копии до отказа; RTO неизвестен до измеренного теста восстановления. Восстановление нескольких систем выполняется независимо.

## OI Registry: 9 стадий

1. Получить полный `oi-registry-*.tar.gz` и соответствующий `.sha256` через защищённый носитель. Убедиться, что документирован нужный момент времени и версия программы.
2. Проверить целостность: `bash /path/to/verify_backup.sh /path/to/oi-registry-XXX.tar.gz`. При ошибке прекратить процедуру.
3. На **новой** VM установить заранее проверенные Debian/Docker/Compose **офлайн**; обеспечить локальные копии используемых образов или разрешённый внутренний registry.
4. Извлечь архив во временный закрытый каталог:

   ```bash
   umask 077
   mkdir -m 700 -p /root/oi-restore
   tar -xzf /path/to/oi-registry-XXX.tar.gz -C /root/oi-restore
   mkdir -m 700 -p /srv/oi-restored
   tar -xzf /root/oi-restore/application.tar.gz -C /srv/oi-restored
   install -m 600 /root/oi-restore/config.env /srv/oi-restored/.env
   ```

   Не выполнять эти команды на действующей установке. Файлы могут содержать секреты; очистка временных файлов — только после фиксации результата DR.
5. Обязательно отключить **все исходящие интеграции** тестовой копии: `OI_OP_SYNC_ENABLED=false` в локальной `.env`, закрыть сетевой доступ к production OpenProject, отключить автоматический worker, пока база не проверена.
6. Запустить **только** новый PG: `cd /srv/oi-restored && docker compose up -d oi-db`, дождаться `healthy`. Проверить, что БД пуста и API ещё не стартовал. `postgres:17-alpine` должен соответствовать формату резервной БД.
7. Импортировать PostgreSQL logical dump **только в пустую базу**:

   ```bash
   docker compose exec -T oi-db pg_restore -U oi_registry -d oi_registry      --no-owner --no-privileges --single-transaction      < /root/oi-restore/database.dump
   ```

   Если база не пустая, **не используйте `--clean`** как неосмысленный обход проблемы. Создайте новую чистую тестовую базу после проверки причины.
8. Восстановить `documents.tar.gz` в пустой volume документов по инструкции, входящей в исходный release `docs/BACKUP_AND_RESTORE.md`. Проверить отсутствие опасных путей/ссылок архивов перед распаковкой. Пример из release использует доверенный контейнер приложения и Python `tarfile.extractall(...,filter='data')`; адаптировать версию Python при необходимости и проверить UID/GID файлов (обычно UID 10001).
9. После восстановления запустить `oi-api`/`oi-web` (без worker и publish), проверить `alembic current` (v0.4 `0005_automation`), HTTP health, аутентификацию, количество ОИ/СВТ/документов, доступ к вложениям, журнал аудита, отчёты. Провести изолированное тестовое планирование с `--dry-run`. Только после протокола принимать решение о production-переключении.

## OpenProject: самостоятельное восстановление

OpenProject не следует восстанавливать средствами Docker CMDB. На отдельной Debian VM установить **совместимую** версию OpenProject (`17.9.1` или версию архивного снимка) и использовать официальную для **этой версии пакета** процедуру восстановления `openproject run restore` / компонентных backups после проверки фактических возможностей команды:

```bash
sudo openproject help
sudo openproject run bundle exec rake version
```

Не запускать потенциально удаляющие/перезаписывающие restore-команды без отдельного утверждённого плана. Проверить комплект DB, attachments, Git/SVN, config, SSL/TLS и пользователей. После восстановления OpenProject проверить реальные project IDs, чтобы CMDB не создавала задачи в неверном проекте.

## IB Platform: самостоятельное восстановление

Восстановить PostgreSQL `ibplatform` **в пустую БД**, исходники/совместимые Compose-слои, volume документов, RAG индекс/версии (в БД), секреты/сертификаты/профили, модели Ollama и Open WebUI хранилище. Если доступен только dump PG, **не считать систему восстановленной**: оригиналы документов и модели могут отсутствовать. В тестовой копии отключить внешние интеграции, сначала проверить lexical FTS, затем по желанию маленькие модели.

## Приёмка DR

- Зафиксировать RTO, исходный бэкап и SHA256, версии Debian/PG/Alembic, число восстановленных объектов и файлов, результат login/HTTP/функций.
- Сравнить фактическое состояние с контрольным реестром активов/документов, проверить аудит и права.
- Не переносить `.env` с действующими prod токенами в открытую испытательную сеть; по окончании учений отзывать/изолировать задействованные секреты.
- Заполнить [RECOVERY-TEST.md](../templates/RECOVERY-TEST.md). Если тест не прошёл — не объявлять копии пригодными к восстановлению.
