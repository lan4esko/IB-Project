# Технические требования OI Registry v0.6 и трассировка к реализации

**Редакция:** 20.10.2026. **Источник требований:** согласованные в обсуждении схемы ОИ/СВТ и запросы на ремонтную историю, перенос каждого ОИ и аварийное извлечение. Это **рабочая спецификация**, а не подписанное организацией формальное ТЗ или нормативный документ. Для эксплуатационной приёмки нужна утверждённая редакция.

## Статусы

- **Реализовано** — подтверждено переданным кодом; приёмка на PostgreSQL может оставаться незавершённой.
- **Частично** — есть отдельный компонент, но требование не выполнено полностью.
- **Запланировано** — соответствующей функции в v0.6-alpha нет; нельзя обещать пользователю.

| ID | Требование | Статус в исходниках v0.6-alpha | Где проверять / недостающее |
|---|---|---|---|
| OI-01 | Паспорт ОИ: название, код, классификация, местонахождение, состояние, даты аттестации | Реализовано (базовый набор) | `app.models.InformationObject`; поля импорта в `app.object_transfer.OI_FIELDS` |
| OI-02 | ОИ объединяет отдельные СВТ с инвентарными и заводскими номерами | Реализовано | `InformationObject`, `Asset`, `/api/objects`, `/api/assets` |
| SVT-03 | «Карточка болезней»: даты и содержание ремонтов СВТ | Частично | `work_entries`, `service_requests`; нет полного единого медицинского паспорта/аналитики в новой UI |
| SVT-04 | Обновлённая история замен комплектующих и причин неисправностей | Частично | `asset_components` и `work_entries` есть; новые расширенные поля диагноза/простоя для v0.6 ещё не внедрены |
| OI-05 | Выгрузка одного ОИ в читаемый автономный ZIP | Частично | Есть JSON паспорта, СВТ и CSV историй; **нет** оригиналов документов, полных связанных сущностей |
| OI-06 | Импорт одного ОИ с сохранением всех документов и истории | Запланировано | В alpha импортируются **только** поля паспорта и СВТ |
| OI-07 | Перед КАЖДЫМ импортом предложить три варианта `merge`, `copy`, `replace` | Реализовано | `POST /api/objects/transfer/preview`; сервер требует `mode`, возвращает сравнение 3 вариантов |
| OI-08 | Отдельно переспросить перед транзакцией; запретить повтор | Реализовано | `POST /api/objects/transfer/commit`, одноразовый `TransferApproval`, 10 минут, проверка архива/состояния |
| OI-09 | Подтверждение при **любом** редактировании карточек в системе | Запланировано | Обычные `PATCH`/CRUD обходят двухэтапную процедуру переноса |
| OI-10 | Экспорт на аварийное чтение без работающего приложения | Частично | CSV+JSON можно открыть локально; неполный состав сведений |
| OI-11 | Полный аварийный бэкап PostgreSQL и файлов с проверкой восстановления | Частично | `backup_full.sh` и `verify_backup.sh` есть; внешний защищённый носитель и DR-тест не подтверждены |
| OI-12 | Помещения/РП: корпус, кабинет, зоны `Rв`, `Rн`, смежность | Запланировано | Поля `Rв`, `Rн` **текстовые**; `rooms`/смежность не реализованы |
| OI-13 | ТС = технические средства, они же средства технической защиты информации | Частично | `asset_security_tools` не равнозначен единому реестру физических ТС/СрТЗИ со всеми реквизитами |
| OI-14 | Должностное лицо: ФИО, числовое `АТС-Р`, `допущен` (`BOOLEAN`) | Запланировано | Нет отдельной завершённой сущности лиц с указанным набором полей |
| OI-15 | `ПЗР`, `ТРД` — учётные номера документов | Запланировано | Рекомендуемый тип `VARCHAR`, а не число, т.к. возможны буквы/нули |
| OI-16 | `КЗ`, `Rв`, `Rн`, `ОТСС`, `ВТСС` — текстовые поля | Запланировано | Смысл категорий/наборов согласовать отдельно; не вводить искусственные числа/BOOLEAN |
| OI-17 | `R2`, `r1`, `r1′` и категорийные значения на исходной схеме | Требуется уточнение | Пока не зафиксированы домены значений; **не** создавать колонки без пояснения владельца процесса |
| GOV-18 | Мероприятия ИБ, ответственные, расписание | Реализовано в v0.5 | `0006_control_rules`, `ControlRule`, `PlannedActivity`; приёмка на PostgreSQL 18.10 |
| OP-19 | Публикация в OpenProject без автоматического создания дублей | Частично | Ручная публикация и ручная сверка статуса; нет сквозного двустороннего процесса |

## Правила проектирования дальнейшего релиза

1. Запрещено выдавать частичную v0.6-alpha за полное восстановление ОИ.
2. Для всех импортируемых связанных записей необходимо определить устойчивые идентификаторы, сопоставление на новом сервере, историю изменений, аудит и понятный план отката.
3. Три режима и повторное подтверждение относятся **к каждому импорту**; расширение на обычное редактирование данных — отдельная доработка после согласования.
4. ТЗ не создаёт SQL-поля автоматически. Изменения моделей и ограничений требуют новой миграции, проверки на копии PostgreSQL и утверждения данных/прав.
5. Не использовать недоказанные нормативные сроки, лицензии или статусы соответствия средств ТЗИ.

## Условия следующей версии

Перед работой над полноценным переносом уточнить перечень документов/их юридический статус, правила правомерного копирования ОИ, возможность нескольких владельцев/ответственных, обработку конфликтов, полную структуру помещений/ТС и состав истории ремонтов. Приоритет — отсутствие потери данных и возможность проверить экспорт без запуска приложения.

| OI-20 | Аттестационный документ как текстовая ссылка на SMB | Реализовано в коде (не внедрено) | `InformationObject.attestation_smb_path`, `0008_registry_v061`, веб-форма |
| SVT-21 | СВТ независимо от наличия ОИ | Реализовано в коде (не внедрено) | `Asset.oi_id nullable`, `outerjoin`, форма/тесты |
| SVT-22 | CSV импорт/экспорт СВТ с 3 вариантами и повторным подтверждением | Реализовано в коде (не внедрено) | `asset_csv.py`, API `POST /api/assets/import/{preview,commit}`, JS |
| REQ-23 | Отдельный раздел «Заявки»: сегмент, ФИО, IP, SMB-скан, СВТ; без поля «Тип системы» (уточнение v0.6.2) | Реализовано в коде v0.6.2, не проверено на PostgreSQL | `RegistryRequest`, миграция `0009`, API/UI; прежний `system_type_id` сохранён только как история |
| TLS-24 | HTTPS веб-панели, включая проброс порта VirtualBox NAT | Конфигурация подготовлена, приёмка не проведена | `compose.https.yaml`, `nginx.https.conf`, [инструкция](../operations/OI-REGISTRY-V061-HTTPS.md) |

**Особенности совместимости:** привязку `oi_id` сделали необязательной, но ОИ-специфичные функции (комплекты, правила контроля для ОИ, МФУ ОИ) требуют предварительного назначения СВТ объекту. Никакого автоматического SMB-доступа к скану приложение не предоставляет.
