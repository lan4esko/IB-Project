## Структура данных

Основные модели: `InformationObject`, `Asset`, `FieldDefinition`, `FieldValue`, `FieldEvidence`, `Document`, `ServiceRequest`, `WorkEntry`, `AssetComponent`, `AssetInspection`, `PlannedActivity`, `ControlRule`, `TransferApproval`, `AuditEvent`. Полный обзор: [модель данных](../data/OI-DATA-MODEL.md).

- **Паспорт ОИ:** код/название, класс/категория, расположение, статус, даты и идентификатор аттестации, план уведомлений, внешний ID OpenProject.
- **СВТ:** заводской и инвентарный номер, ОС, модель, сетевые параметры и принадлежность к ОИ; состав компонентов и работы хранятся **отдельно**.
- **«Карточка болезней»:** `service_requests` (неисправность/заявка) и `work_entries` (выполненная работа) уже существуют; новая сводная карточка, диагнозы и интервалы простоя **план**.
- **Мероприятия ИБ:** `ControlRule` задаёт частоту/назначения, `PlannedActivity` хранит план/факт, доказательства и ссылки на OpenProject. Требования регламентов задаёт уполномоченный человек.
- **Перенос ОИ:** ZIP alpha передаёт **только ограниченный паспорт/СВТ**; CSV ремонта/заявок не являются импортом в новую БД.

## Роли

- `admin` — администрирование, настройка, публикация, перенос ОИ; текущие два новых transfer endpoint доступны только ему.
- `editor` — редактирование карточек и обслуживание в пределах политики текущего API, не может выполнить admin transfer.
- `requester` — заявка по ОИ, не равна официальной записи реестра.
- `viewer` — чтение разрешённых данных.

Per-OI ACL необходимо подтверждать перед работой с чувствительными данными: наличие ролей не доказывает полного разграничения по объектам.

## OpenProject и планировщик

`oi-worker` создаёт локальные записи по регламентам. Задачи OpenProject не публикуются автоматически; администратор вручную вызывает publish. Для v0.5 предусмотрена ручная сверка удалённого статуса; **нет** непрерывной двусторонней синхронизации. ОИ-бэкап не восстанавливает OpenProject. [Интеграция](../integrations/OPENPROJECT-API.md).
