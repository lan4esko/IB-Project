# OI Registry v0.6-alpha — импорт/экспорт с подтверждением

**Статус:** экспериментальная функция на отдельном тестовом экземпляре. **Не** полноценный перенос всех сведений об ОИ и **не** релиз для рабочей базы. Контракт ZIP подробно описан в [формате данных](../data/OI-TRANSFER-FORMAT.md).

## Сценарий администратора

1. Войти в тестовый интерфейс (`18085` по журналу тестовой установки) под тестовым `admin`.
2. Вкладка **«Перенос ОИ»** → выбрать существующий ОИ → скачать ZIP. Хранить только в защищённом расположении. Не размещать в Git или общедоступной папке.
3. Для импорта выбрать ZIP, **явно выбрать один из трёх вариантов** и нажать «Показать предварительные изменения». По умолчанию режим не задан.
4. Сравнить **все три** оценки изменений, прочитать `conflicts`, номера и количество добавляемых, изменяемых и выводимых из эксплуатации СВТ. `merge` при конфликтах заблокирован.
5. Подтвердить чекбоксом ознакомление, **вручную** набрать показанную сервером уникальную фразу и отдельно нажать подтверждение транзакции.
6. Сервер повторно проверяет автора, режим, ZIP/SHA256, актуальность карточки ОИ и СВТ, время (10 минут), одноразовость; только затем обновляет данные и записывает аудит.
7. При HTTP 409 операция отменяется; сформировать новое превью. При HTTP 403 проверить права/подтверждение. Не повторять `commit` вслепую.

| Режим | Если ОИ существует | Если ОИ не существует |
|---|---|---|
| `merge` — объединение | Сохранить паспорт и совпадающие СВТ, добавить отсутствующие; различия полей блокируют операцию | Создать ОИ и СВТ |
| `copy` — отдельная копия | Создать ОИ/СВТ с кодами `-COPY-XXXXXXXX`; существующий не трогать | Создать копию со специальным кодом |
| `replace` — заменить паспорта | Обновить паспорта; отсутствующие СВТ отметить `retired`, без физического удаления | Заблокировать до выбора другого режима |

**Сфера действия подтверждения:** **только этот импорт ОИ**. Прямые CRUD/PATCH-маршруты существующих карточек не используют `TransferApproval`; требование «спрашивать перед любой правкой в системе» ещё не реализовано.

## Техническая реализация

- `GET /api/objects/{oi_id}/transfer.zip` (admin) → ZIP из `object_transfer.export_oi`.
- `POST /api/objects/transfer/preview` (admin) → ZIP + `mode=merge|copy|replace` → `TransferApproval` + сравнительный отчёт и `confirmation_phrase`.
- `POST /api/objects/transfer/commit` (admin) → тот же архив, тот же режим, `plan_id`, уникальная фраза → проверка записи (в PostgreSQL блокировка `FOR UPDATE`) → `apply()` + аудит + `COMMIT`.
- Ревизия Alembic: `0007_oi_transfer_approvals` над `0006_control_rules`; миграция создаёт таблицу для одноразовых согласований.
- Лимиты ZIP: 8 МиБ передача, 16 МиБ распаковка, до 3000 СВТ. Подписи архива нет.

### Граница восстановления

В ZIP **не содержатся** оригиналы документов, договоры/акты, документы аттестации, пользовательские поля, компоненты, ремонты как сущности БД, заявки, история мероприятий, OpenProject. CSV ремонтов/обращений предназначены **только для человека**, не восстанавливаются импортом. Паспорта ОИ/СВТ — не полные строки ORM (например, нет связей с документами/OpenProject).

Поэтому перед тяжёлыми операциями на реальных данных использовать `scripts/backup_full.sh`, проверить контрольные суммы, сохранить зашифрованную внешнюю копию и испытать восстановление в отдельном окружении. Снимок Git не является резервной копией БД.

## Развёртывание и диагностика без влияния на production

Две изолированные установки используют разные Compose project, PostgreSQL volumes и HTTP-порты. Для тестового проекта рабочая папка по журналу: `/home/admsec/ZGT-v06-test/CMDB/oi-registry-v0.1`. **Нельзя** запускать его со стандартным именем проекта `oi-registry`.

```bash
cd /home/admsec/ZGT-v06-test/CMDB/oi-registry-v0.1
# Перед действиями только чтение; пароль/secret не печатать.
docker compose -p oi-registry-v06-test config -q
docker compose -p oi-registry-v06-test ps
docker compose -p oi-registry-v06-test exec -T oi-api alembic current
curl -fsS http://127.0.0.1:18085/api/health/ready
```

Ожидаемая миграция тестовой версии: `0007_oi_transfer_approvals (head)`, **пока не показана администратором в журнале**. Показанный вход на `18085` подтверждает работу UI/авторизации, но не все проверки бизнес-логики.

**Осторожно:** `scripts/create_admin.sh` внутри себя вызывает `docker compose` без `-p`, поэтому при нескольких инстансах надо явно передавать `COMPOSE_PROJECT_NAME=oi-registry-v06-test` на время запуска. Перед созданием новых УЗ проверьте фактическую БД.

Для тестов в окружении с установленными зависимостями из `backend/requirements.txt`:

```bash
cd /home/admsec/ZGT-v06-test/CMDB/oi-registry-v0.1
python3 -m pytest -q tests/test_object_transfer_v06.py
python3 -m pytest -q tests/
```

Проверки на SQLite не заменяют приёмку `FOR UPDATE`, транзакций и восстановления на PostgreSQL. Сценарии приёмки: [чеклист](OI-REGISTRY-V06-ACCEPTANCE.md).
