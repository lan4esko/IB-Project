# Связь OI Registry → OpenProject REST API v3

**Статус:** [ИСХОДНИК] есть ручная публикация одной записи из OI Registry v0.4, **не активируется автоматически**. [ФАКТ] 18.10 `sync_status=not_sent`, в `oi-worker` нет отправки. Обратная синхронизация статусов задач — [ПЛАН].

## Контракт

- Источник: `planned_activities` OI Registry; ключ `event_key` (например `inspection:1:2026Q4`).
- Назначение: Work Package **в заранее проверенном** проекте `information_objects.openproject_project_id`.
- Тип: явный `OI_OP_TYPE_ID`, удостовериться, что тип разрешён в выбранном проекте OpenProject.
- Авторизация: отдельный малопривилегированный OpenProject API key через Basic auth (`apikey` / token), без печати секрета.
- Ссылка обратно: `openproject_work_package_id`, состояние публикации и время/ошибка.
- Публикатор: admin endpoint `POST /api/automation/activities/{id}/publish` по одной записи после проверки.

## Подготовка (только после создания сервисного аккаунта)

Сервисная учётная запись имеет только требуемые права на нужные проекты. В `/home/admsec/ZGT/CMDB/oi-registry-v0.1/.env` вручную, **не вставляя значения в Git**:

```dotenv
OI_OP_SYNC_ENABLED=true
OI_OP_BASE_URL=https://REPLACE-WITH-REAL-LOCAL-OPENPROJECT
OI_OP_API_KEY=REPLACE-LOCALLY-DO-NOT-COMMIT
OI_OP_TYPE_ID=REPLACE_WITH_VERIFIED_TYPE_ID
```

`OI_OP_ALLOW_LOCAL_HTTP=true` допустим **лишь для подтверждённого локального HTTP с `host.docker.internal`** на тестовом стенде; в постоянном контуре TLS. Если путь из контейнера отличается от хостового адреса, сначала проверять DNS/маршрут без раскрытия ключа. После настройки: `docker compose up -d --no-deps --force-recreate oi-api`, затем `GET /api/automation/integration` под admin.

## Первый тест

1. Создать **тестовый** ОИ/СВТ с настоящим ID тестового проекта OpenProject.
2. Сверить допустимый тип Work Package и права сервисной УЗ.
3. Просмотреть сформированную карточку мероприятия: её заголовок должен быть читаемым. В предыдущем логе был ошибочный `1u2n: ...` — перед публикацией выяснить значение кодов ОИ/СВТ.
4. Ручная публикация **одной** карточки; сверка созданного work package через OpenProject UI и его ID.
5. Второй запрос на ту же карточку должен блокироваться; проверка корректности защиты от дублей.
6. При `needs_review` **не повторять** API POST: найти work package в OpenProject по уникальному ключу `[OI-REGISTRY:...]`, сверить с БД, затем решать инцидент вручную.

## Не реализовано

Автоматическое назначение исполнителя, массовая публикация, чтение статусов выполненных задач обратно, автозакрытие work package при инспекции, создание проектов OpenProject из OI Registry, webhook и сверка без ручного контроля. Реализовать в отдельной версии с журналами запросов и учётом дубликатов при timeout.

## Ошибки

- 401 → токен неверный/отключён; проверить на стороне OpenProject, без вывода токена.
- 403 → сервисная УЗ не уполномочена для проекта/типа.
- 404 → неверный base URL, проект или маршрут.
- 422 → формат payload, ID типа, обязательные custom fields проекта; проверить HAL-формат API v3.
- timeout или 5xx после POST → возможна созданная задача, обязательна ручная сверка по ключу.
