# OI Registry v0.6.1-alpha — учёт СВТ, заявки и ремонтные работы

**Статус:** кандидат для тестового стенда, не выполнять миграцию `0008` на рабочем PostgreSQL до тестового восстановления резервной копии.

## 1. Что меняется

- У ОИ появляется `attestation_smb_path` (`TEXT`): буквальный SMB URI `smb://server/share/file.pdf` или UNC `\\server\share\file.pdf`. Путь — **только ссылка**, API не подключается к SMB и не проверяет наличие файла. Старое поле `attestation_document_id` сохраняется только ради существующих данных и совместимости старого API. Не вводите ID в новую веб-форму.
- `assets.oi_id` допускает NULL: СВТ можно поставить на учёт независимо от ОИ и назначить ОИ позднее, без смены идентификатора и потери истории. Связанные с ОИ функции (МФУ, планирование по ОИ) недоступны, пока СВТ не закреплена.
- В меню **«Заявки»** отдельная таблица `registry_requests`: `segment`, `full_name`, `ip_address`, `scan_smb_path`, `asset_id`. Начиная с v0.6.2 поле «Тип системы» и редактор типов в интерфейсе отсутствуют; для старых записей ссылка `system_type_id` сохраняется в БД, для новых равна NULL. Исторические `oi_proposals` и `service_requests` **не удаляются**.
- **Реестр СВТ → Выгрузить полный CSV → Импорт CSV**. Необходимо сначала выбрать один из трёх режимов (`merge`, `copy`, `replace`); сервер возвращает сравнение всех вариантов и одноразовое согласование. Вторая операция с тем же архивом и подтверждающей фразой допускает один `commit`, повтор запрещён; изменения после предпросмотра требуют новый просмотр. Режим `replace` обновляет только совпадающие коды, новые коды добавляет, отсутствующие строки **не удаляет**. Не импортируются пользовательские поля, журнал ремонтов или вложения.
- В ZIP-переносе ОИ сохраняется `attestation_smb_path`, но **старый ZIP уже мог быть создан без этого поля** — его импорт допускается с пустым SMB-путём, если все остальные ключи соответствуют ожидаемому формату.

## 2. Ведение истории ремонтов СВТ через веб-панель

1. В «Реестр СВТ» найдите компьютер по коду, инвентарному номеру либо серийному номеру.
2. Откройте карточку → **«Состав, работы, проверки»** → блок **«Заявки о неисправностях и журнал работ»**.
3. Если работу инициировала неисправность, создайте обращение (дата, заявитель, описание). Для профилактики обращение необязательно.
4. В форме журнала работ укажите `performed_at`, `performer`, `work_type` (`diagnostics/repair/replacement/configuration/preventive/other`), `actions`, `result`, `seal_state_after`, при необходимости `seal_note`, страницу и документ. Опционально свяжите запись с ранее созданным обращением.
5. Если заменяли SSD/БП/другой компонент, в разделе «Комплектующие» выведите старый компонент из состава и заведите новый с заводским номером. Ссылку на акт прикрепите к операции. Не меняйте старую запись ремонта — новая запись должна сохранять историю.
6. После закрытия неисправности оформите решение в связанном обращении. Список работ доступен даже для СВТ, временно не закреплённой за ОИ.

Важно: новая табличная **«Заявки»** — это реестр административных запросов на доступ к типам систем, а `service_requests` в карточке СВТ — обращения о неисправностях. Это независимые процессы.

## 3. Миграция `0008_registry_v061`

Добавляет `attestation_smb_path`, переводит `assets.oi_id` в nullable, создаёт `system_types` и `registry_requests`. Ни существующие СВТ, ни старые ремонтные записи миграция не удаляет. На **тестовой** PostgreSQL после согласованного бэкапа:

```bash
cd /home/admsec/ZGT-v06-test/CMDB/oi-registry-v0.1
docker compose -p oi-registry-v06-test -f compose.yaml -f compose.https.yaml config -q
# Только после подтверждения и проверки бэкапа:
# docker compose -p oi-registry-v06-test -f compose.yaml -f compose.https.yaml up -d --build oi-api oi-web oi-tls
# docker compose -p oi-registry-v06-test -f compose.yaml -f compose.https.yaml exec -T oi-api alembic current
```

Откат `0008` блокируется, если есть незакреплённые СВТ либо записи в новом журнале заявок. Удаление `attestation_smb_path` при downgrade теряет ссылки; вместо автоматического downgrade восстановите согласованный полный снимок при необходимости.

## 4. Остановка старых проектов без удаления данных

Просмотр (без изменений):

```bash
docker compose ls --all
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}\t{{.Label "com.docker.compose.project"}}'
```

После сверки и подтверждения имени **старого** проекта, например `oi-registry` на 8085:

```bash
cd /home/admsec/ZGT/CMDB/oi-registry-v0.1
docker compose -p oi-registry --profile automation stop
```

`stop` завершает контейнеры, **не удаляя volumes**. Не запускайте эту команду, если v0.5 остаётся рабочей. Для обратного запуска `docker compose -p oi-registry --profile automation start`. `down -v`, `docker volume prune` и массовые `docker stop $(docker ps -q)` здесь запрещены.

## 5. Проверки приёмки

- Тестовый `alembic current` выводит `0008_registry_v061 (head)`; PostgreSQL-контейнер здоров.
- Создание ОИ со строковым SMB-путём не требует `attestation_document_id`.
- Создание СВТ без ОИ, просмотр и ведение работ; позже привязка к ОИ.
- Создание двух заявок без типа системы, изменение заявки, проверка аудита и сохранение старых записей.
- CSV: предпросмотр всех 3 режимов, неверное подтверждение, повторное использование, конкурирующее изменение, успешный новый импорт.
- HTTPS в браузере без предупреждения о сертификате; cookie `Secure`; HTTP-порт не доступен из сторонней сети.
- Исходники и документация проходят тесты. Публикация в GitHub только после ревью `git diff`, секретов и Pull Request.
