# Контроль мероприятий v0.4

## Данные

Таблица `planned_activities` хранит контрольные события. Уникальный `event_key` препятствует дублированию. При переаттестации ОИ новое мероприятие связано с новой датой, а прежнее сохраняется в истории с состоянием `superseded`. При регистрации проверки текущего квартала контрольная запись переходит в `satisfied`. Эта отметка не доказывает устранения замечаний.

## Роли и аудит

- `admin`: просмотр, планирование, ознакомление и ручная публикация в OpenProject (после включения).
- `editor`: просмотр, планирование и ознакомление, публикация запрещена.
- `requester`: только заявки по ОИ, доступ к общему реестру мероприятий запрещён.
- Аудит действий пользователей фиксирует учётную запись, действие, объект, время, request-id.

## Изоляция и интеграция

`oi-worker` работает через отдельный контейнер и обращается только к PostgreSQL, не имеет API-ключа OpenProject. `oi-api` получает API-ключ из закрытого `.env` только при явной настройке. OpenProject не имеет прямого доступа к PostgreSQL OI Registry. Задачи публикуются через HTTPS API v3 от сервисного пользователя. Таймауты нельзя безопасно повторять без проверки: удалённая задача могла успеть создаться.

## Параметры проекта

В карточке ОИ указывается `openproject_project_id` (числовой ID), `attestation_valid_until` и `attestation_notice_days`. При отсутствии даты срок не рассчитывается автоматически. Для СП/СИ, ремонтов, паспортов СВТ и внешних проверок в дальнейшем добавляются отдельные типы мероприятий, но в v0.4 они не запускаются автоматически.


## Изменения v0.5 — контроль регламентов

Администратор создаёт `control_rules`: название, область (`oi`/`asset`), конкретный ОИ или все ОИ, дата первого срока, интервал в месяцах (1/3/6/12), ответственный. **Ни одно правило по нормативным требованиям не создаётся автоматически.** Сроки и применимость утверждает ответственное лицо по локальным регламентам. Для 60 ОИ и ~20 СВТ в каждом поддерживаются глобальные правила с автоматическим построением отдельных записей и постраничной выдачей.

Планировщик создаёт события в окне от 90 дней до даты запуска до 90 дней вперёд. Уникальный `event_key` препятствует дублированию; завершённые события не переоткрываются. Старые периоды не восстанавливаются автоматически за много лет. Если правило выключается, незавершённые записи становятся `superseded`; уже опубликованные задачи OpenProject нужно сверить вручную. Повторное включение правила не оживляет отменённые записи.

Состояние `completed` записывается только после явного действия оператора/администратора, с обязательным документом из таблицы `documents`, текстом и записью в `audit_events`. Статус `satisfied` из v0.4 по квартальной проверке означает **наличие зарегистрированной проверки**, а не устранение замечаний. Для OpenProject предусмотрен ручной запрос статуса GET `/api/v3/work_packages/{id}`; удалённый `Closed` **не завершает** локальное мероприятие. Сбой GET не раскрывает секрет в ответе.

API v0.5: `GET/POST /api/automation/rules`, `POST /api/automation/rules/{id}/disable`, `/enable`, `GET /api/automation/summary`, `POST /api/automation/activities/{id}/complete`, `/reconcile`. `GET /api/automation/activities` поддерживает параметры `status=pending`, `oi_id`, `event_type`, `offset`, `limit`. Создание/включение/выключение правила и сверка с OpenProject — только `admin`; подтверждение выполнения — `editor` или `admin`; `requester` не видит реестр. Все операции изменения требуют действующей сессии и CSRF-токена.

Миграция `0006_control_rules` сохраняет таблицу `planned_activities`, расширяя её новыми полями. Перед внедрением обязательна полная резервная копия с доказанной проверкой целостности. Возврат схемы через downgrade удаляет записи/поля v0.5 и **не является безопасным способом отката данных** — для возврата к v0.4 требуется полноценное восстановление базы и файлов из согласованной резервной копии.
