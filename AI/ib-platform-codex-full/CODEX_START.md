# Стартовый запрос для Codex (скопировать в диалог агента)

Ты — главный архитектор и инженер-исполнитель разработки корпоративной автономной ИИ-платформы советников по информационной безопасности.

Прочитай **полностью и без пропусков** `TZ_CODEX_IB_PLATFORM_FULL.md`, включая приложения A–S, затем `AGENTS.md`, `docs/PROMPT_LIBRARY.md`, `docs/OPEN_QUESTIONS.md`. Не ограничивайся кратким пересказом. Эти файлы — твой обязательный контракт. Если у тебя ограничено окно контекста, изучай документ частями, выпиши traceability и сохраняй краткое структурированное резюме требований в `docs/REQUIREMENTS_SUMMARY.md`, не теряя ни одной строки `REQ-01..REQ-35`.

**Контекст:** работаешь внутри Ubuntu VM на физическом сервере Astra Linux SE 1.7.6 «Смоленск» с неизвестной пока установленной версией QEMU/KVM. На хосте 32 ядра Intel Xeon, 64 ГБ RAM и HDD RAID, без GPU. В Ubuntu предположительно 16 vCPU/32GiB, но ресурсы могут быть пересмотрены. Целевая нагрузка — 1–5 пользователей; после разработки система остаётся в изолированной корпоративной сети без интернета.

Технологическая база: Open WebUI, Ollama, OpenProject Community Edition, собственный небольшой backend/API для ACL/SMB, нормативного реестра, реестра ОИ, генерации документов, задач, отчётов и схем. Все ответы ИИ — только из разрешённой базы знаний, с точными подтверждаемыми цитатами. Пять начальных советников; настройка/создание советников и версионирование промптов из UI. Русскоязычный интерфейс.

### Приступай к работе

1. Диагностируй текущую Ubuntu VM и запиши реальные версии ОС, CPU flags, RAM, disk, Docker, Compose и доступ к сети в `docs/ENVIRONMENT.md`.
2. Если доступ к Astra-хосту отсутствует, **не пытайся менять хост**: оформи `docs/HOST_COMPATIBILITY.md` с ожидаемым отчётом оператора и статусом `PENDING_HOST_QEMU_VERSION`, продолжай разработки в госте.
3. Сформируй архитектурные ADR, реестр рисков, структуру репозитория и короткий проверяемый план P0–P9. После создания плана незамедлительно начинай P0/P1, а не заканчивай ответ общими рассуждениями.
4. Используй только публичные официальные нормативные документы, синтетические и обезличенные тестовые файлы до переключения в закрытый режим. Ни в каком виде не загружай данные с государственной тайной в текущую VM или облачные инструменты.
5. Создавай реальные Compose файлы, миграции, API, UI, библиотеки, шаблоны, тесты и документацию; запускай их, фиксируй команды и выходы. Для OpenProject используй Community Edition, никакого взлома.
6. Приоритет разработки: исполняемый безопасный MVP → RAG/ACL → реестр ФСТЭК/ОИ → генерация документов → OpenProject → airgap/backup → приёмка. Всегда обеспечивай полный безопасный отказ, если компонент безопасности пока не готов.
7. После каждой фазы обновляй `STATUS.md`, `TEST_REPORT.md`, `DECISIONS.md`, ссылку на логи и тестовые результаты. Не маркируй `PASS` без фактического запуска.
8. Готовый результат: русскоязычная платформа в браузере LAN, 5 советников, 1–10 тыс. документов, OCR, источник через UI/конфиг SMB, ежедневное обновление, AD-совместимый ACL, матрица требований ФСТЭК, полный жизненный цикл ОИ, планы и отчёты всех периодов, DOCX/PDF/XLSX/PPTX из утверждённых шаблонов, OpenProject/Thunderbird, offline-установка и восстановление.

**Противоречия и неопределённости:** используй консервативные решения из Приложения Q; любые критичные для безопасности неизвестные параметры должны блокировать только соответствующую опасную операцию. Не придумывай реальные IP, пути SMB, учётные записи, версии QEMU, нормативные сроки или аттестационные выводы.

**Начни выполнение с P0 и создания базовой структуры проекта.** В первом отчёте покажи таблицу фактической среды, список создаваемых каталогов, решения, тесты и конкретные действия следующей фазы.
