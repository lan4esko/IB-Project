# OI Registry — регламент резервного копирования и восстановления

## 1. Назначение и точные пути

**Что резервируем:** только OI Registry (PostgreSQL `oi_registry`, оригиналы документов, параметры запуска и исходники приложения). OpenProject и IB Platform — независимые системы, их резервные копии делаются отдельно.

**Где работает приложение:** `/home/admsec/ZGT/CMDB/oi-registry-v0.1/` (название каталога сохраняется после обновлений v0.2, v0.3 и следующих).

**Где постоянно находятся переносимые резервные копии:**

```
/home/admsec/ZGT/CMDB/BACKUPS/
  oi-registry-YYYYMMDD-HHMMSS.tar.gz
  oi-registry-YYYYMMDD-HHMMSS.tar.gz.sha256
```

**Что копировать на резервное хранилище:** оба одноимённых файла (`.tar.gz` и `.sha256`) для каждого нужного восстановления. Для простоты можно скопировать *весь каталог `BACKUPS`*. Это уже готовые резервные копии: не нужно искать PostgreSQL volume или собирать файлы из нескольких каталогов.

### Отличие рабочей базы от резервной копии

Живая PostgreSQL 17 **не является одним файлом**. Её файлы находятся во внутреннем Docker volume `oi-registry_oi_postgres_data`. Оригиналы вложений лежат в `oi-registry_oi_documents_data`. **Нельзя** копировать PostgreSQL volume обычным `cp` при работе контейнера. `database.dump` внутри архива — корректный переносимый логический снимок, созданный `pg_dump -Fc`.

## 2. Содержимое одного резервного архива

```
archive oi-registry-20261018-030000.tar.gz
  database.dump         PostgreSQL, формат pg_dump -Fc
  documents.tar.gz      исходные документы из Docker volume
  application.tar.gz    backend, frontend, compose.yaml, scripts, docs
  config.env            подлинные секреты и конфигурация конкретной установки
  manifest.json         метаданные и SHA-256 каждого компонента
```

**Внимание:** архив содержит конфиденциальные данные и секреты `.env`. Доступ только авторизованным администраторам; локальный каталог — `0700`, файлы — `0600`. Переносить по SSH/SFTP на защищённый узел либо копировать на зашифрованный носитель. **SHA-256 не шифрует архив**; обычная общая папка Windows `/media/sf_/` не подходит для постоянного хранения незашифрованных резервных копий.

## 3. Ручной бэкап

На Debian под `root`:

```bash
cd /home/admsec/ZGT/CMDB/oi-registry-v0.1
bash scripts/backup.sh
```

Во время копирования `oi-api` (и существующий `oi-worker`, если он будет добавлен) временно останавливается для согласованности БД и документов. После успеха **или ошибки** скрипт пытается восстановить ранее работавшие сервисы. `oi-db` не останавливается; приложение некоторое время будет недоступно на запись. Выполняйте в согласованное окно обслуживания. Следите, чтобы на диске хватало места для временных файлов.

Новые снимки никогда не заменяют прежние. Ранее созданные вручную бэкапы в `oi-registry-v0.1/backups/` сохраняются: после установки модуля новые копии создаются только в централизованном `CMDB/BACKUPS/`.

## 4. Проверка копии

```bash
cd /home/admsec/ZGT/CMDB/oi-registry-v0.1
bash scripts/verify_backup.sh /home/admsec/ZGT/CMDB/BACKUPS/oi-registry-YYYYMMDD-HHMMSS.tar.gz
```

Команда сверит контрольную сумму всего архива и каждого вложенного элемента, структуру и безопасность путей. Она ничего не меняет в действующей базе. `BACKUP VERIFIED OK` означает целостность файла, **но не успешное восстановление PostgreSQL**. Регулярно проверяйте фактическое восстановление **на отдельном тестовом стенде**.

Для контроля таймера:

```bash
systemctl status oi-registry-backup.timer --no-pager
journalctl -u oi-registry-backup.service -n 100 --no-pager
ls -lh /home/admsec/ZGT/CMDB/BACKUPS/
```

## 5. Автоматическое копирование

Выполнить ОДИН РАЗ (по решению ответственного администратора):

```bash
cd /home/admsec/ZGT/CMDB/oi-registry-v0.1
bash scripts/install_timer.sh
```

Создаются системные `oi-registry-backup.service` и `oi-registry-backup.timer`; резервная копия формируется ежедневно в районе **03:00 по местному времени сервера**, с возможной задержкой до пяти минут. При пропуске запуска из-за выключенного сервера `Persistent=true` запустит задачу после включения.

Отключить расписание:

```bash
systemctl disable --now oi-registry-backup.timer
```

**Удаление старых копий автоматически не включено:** до определения срока хранения, объёма данных, свободного места и независимого внешнего хранилища запрещено удалять резервные данные по одному только возрасту. Администратор должен контролировать свободное место; при заполнении диска будут ошибки резервного копирования и работы сервиса.

## 6. Порядок восстановления на отдельном стенде (DR)

1. Выделить новый сервер или VM (Debian, Docker Compose, PostgreSQL 17 image), **не использовать рабочий сервер для первой проверки**.
2. Передать архив `.tar.gz`, его `.sha256` и скрипт `verify_backup.sh`. Запустить проверку (раздел 4).
3. Создать защищённый временный каталог и распаковать одну резервную копию:

   ```bash
   umask 077
   mkdir -m 700 -p /root/oi-restore
   tar -xzf /path/to/oi-registry-YYYYMMDD-HHMMSS.tar.gz -C /root/oi-restore
   ```

4. Распаковать `application.tar.gz` **в новый пустой каталог приложения**. Скопировать `config.env` в `.env`, выставить права `0600`, ограничить сетевой доступ восстановленного тестового стенда. При необходимости сменить пароли/секреты после восстановления. Для теста отключить интеграции, способные отправлять команды в OpenProject/другие действующие системы.
5. Запустить **только** `oi-db` в новой установке: `docker compose up -d oi-db`. Дождаться Healthy. Не запускать `oi-api`, иначе автоматические миграции создадут таблицы до импорта.
6. Восстановить логический снимок **в пустую PostgreSQL-БД**:

   ```bash
   cd /path/to/new/oi-registry
   docker compose exec -T oi-db pg_restore -U oi_registry -d oi_registry \
     --no-owner --no-privileges --single-transaction \
     < /root/oi-restore/database.dump
   ```

   При непустой БД команда может завершиться ошибкой. **Не используйте `--clean` без отдельного плана**: это удаляет существующие таблицы.
7. Восстановить оригиналы документов в **пустой** том `oi_documents_data` (операция на новом стенде):

   ```bash
   cd /path/to/new/oi-registry
   docker compose run --rm --no-deps -T --entrypoint python oi-api -c \
     'import sys,tarfile; t=tarfile.open(fileobj=sys.stdin.buffer,mode="r|gz"); t.extractall("/data",filter="data")' \
     < /root/oi-restore/documents.tar.gz
   ```

   Файлы после восстановления должны принадлежать пользователю контейнера `oi` (UID 10001). Проверить при необходимости. Не восстанавливать произвольный непроверенный архив: перед извлечением обязательно запускать проверку.
8. Запустить API и веб-интерфейс: `docker compose up -d oi-api oi-web`. Проверить `/api/health/ready`, `alembic current`, вход пользователя, открытие вложений, историю СВТ, недельные отчёты и соответствие числа записей исходному реестру.
9. Протоколировать результат тестового восстановления (дата, архив, оператор, длительность, число записей, замечания) и хранить его вместе с регламентом.

## 8. Критические ограничения

- **Один каталог на одном диске — не полноценная резервная стратегия.** Копируйте архивы на независимое защищённое хранилище; желательно использовать отдельные права, хранение неизменяемых копий и регулярное тестовое восстановление.
- Этот модуль защищает OI Registry, **не OpenProject, не IB Platform, не Ollama**.
- Исторические версии и документы сохраняются в логической базе/хранилище. Снимок даёт состояние на дату копирования, не защищает от изменений после этой даты.
- Не храните пароли в отчётах и не отправляйте содержимое `.env` или резервные архивы в открытые каналы.
- Рекомендуется вести журнал резервного копирования, проверять уведомления об ошибках timer и согласовать целевые RPO/RTO с владельцем системы.
